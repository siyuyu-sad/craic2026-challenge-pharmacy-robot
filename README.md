# 智慧药房无人配送小车 — 第 28 届中国机器人及人工智能大赛「护航者」赛项

一辆 EPRobot V2.0 小车在 4 分钟限时内跑完「识别处方二维码 → 到体检窗口取样本 → 送到对应化验窗口 → 回报裁判系统」的闭环。仓库是比赛现场实际跑的代码，外加对每个模块设计取舍的复盘。

- 赛事：第 28 届中国机器人及人工智能大赛 · 护航者赛项
- 队伍：3 人。我负责建图、导航定位、文字识别、双车通信（任务调度与裁判上报协议为本仓库主体）
- 平台：EPRobot V2.0，底盘 MCU STM32F407VET6※，激光雷达 SLAMTEC RPLIDAR A1（手册标注 A1M8）
- 软件栈：Ubuntu 18.04 + ROS Melodic + Python 2.7 + OpenCV 3.2 + pyzbar + Tesseract 4（chi_sim）+ move_base/AMCL

> ※ STM32F407VET6：用户提供的信息写作 "STM32F407VET62"，标准料号为 STM32F407VET6（LQFP100/512KB Flash/带以太网 MAC），据料号规则归一化，待与实物丝印确认。

## 三个节点

### 1. `F1_yaofang.py` — 任务调度 + 裁判上报（490 行）

状态机只有三个状态（`count=9/10/11`），一轮跑完回到 9，靠 `rospy.sleep(0.1)` 空转轮询（`:232-239`）。所有导航点写死在 `waypoints`（`:185-197`），姿态由 10 个欧拉角逐个转四元数（`:179-183`）。

**裁判上报**（`StateReporter`，`:19-158`）是这份代码里唯一和「规则」强耦合的部分：

- TCP 连裁判软件 `192.168.31.21:8888`，`settimeout(3.0)`，连接失败不阻塞主流程（`:61-79`）
- 独立线程 1 Hz 上报，断线后每 5 s 重连一次（`:126-148`）
- 报文是单行 JSON + `\n`：`{"id","speed","odom":[x,y],"task","CV1","CV2"}`（`:102-124`）
- `task` 是当前阶段码（`1`/`2`/`4`/`A`/`B`/`C`/`R`），每个阶段入口 `update_task()` 同步更新上报值（`:241-243`）
- `CV1` 闲置未用，`CV2` 填识别结果，格式 `"<窗口组合>-<样本类型>"`，如 `"AB-2"`（`:308-314`）
- 到达任务点后 `odom` 用**标定坐标**而非实时里程计（`ideal_coords`，`:30-40, 88-94`）——底盘 odom 在多次 clear_costmaps 后会有厘米级漂移，直接上报实时值会让裁判端位置判定抖动

**容错**：识别 3 s 收不到合法结果就回退「ABC 三窗口、3 份、组织样本」（`:324-332`），保证比赛不因一次识别失败而空跑。

### 2. `F1_detect_code.py` — 处方二维码识别（408 行）

摄像头画面不是从 ROS 话题拿的，而是 `cv2.VideoCapture("http://192.168.31.101:8080/stream?topic=/camera/rgb/image_raw")` 直接吃 MJPEG 流（`:101`）——绕过 image_transport 的编码转换，省掉一次序列化。

识别链路（每帧）：

1. **旋转补偿**：整帧 `warpAffine` 逆时针转 5°（`:113-122`）。车停在识别板前时车身姿态不保证正对，固定 5° 是实测最优的折中。
2. **找定位框**：Canny(50,150) → 轮廓 → 三层筛选 —— 面积 500–20000（`:143-148`）、`approxPolyDP` 后为四边形（`:150-158`）、长宽比 `|w-h|/(w+h) < 0.4` 视为正方形（`:160-169`）、两两中心互相包含且中心距 < 20 px（`:171-195`）。
3. **个数门限**：定位框总数必须落在 **40–56**（`:196-202`）。原版是 `== 48` 硬等号，斜视/光照变化下常差一两个框，直接把整帧判废；放宽成区间后单帧可用率明显上升（这是本次改动里收益最直接的一处）。
4. **透视归一化**：取四个极值点作为角点，`getPerspectiveTransform` 投到 600×600（`:239-248`），再做一次「左右镜像」判断（`:241-243`），解决车头朝向不同导致四象限对应关系翻转的问题。
5. **切四区域解码**：棋盘四象限各切 150×190 ROI（`:250-261`）→ 灰度 → 固定阈值 127 二值化（`:270-273`）→ `pyzbar.decode`（`:281-284`）。四个区域对应四个化验窗口，解码串是窗口组合（`A`/`AB`/`ABC`/`BC`…）。
6. **投票与上报**：取「解出的字符数最多」的那个区域定样本数（1/2/3），其余区域的串若不在合法集合 `['A','B','C','AB','AC','BC','ABC','',[]]` 里则记 `Error_count`（`:305-336`）。最终发 `/cam_return = [goC,goA,goB,样本数,板位序号,Error_count]`（`:340-391`）。
7. **服务化取结果**：`/request_recognition`（Trigger）不现场识别，而是把最近一次成功结果重发一遍（`:78-92`）。任务节点到板前调一次服务即可，避免「到了才开始识别、还要等 1–2 帧」的时间损失；同时连续 0.5 s 重发一次缓存结果（`:393-399`）兜住调用时机早于识别完成的场景。

### 3. `OCR_CAM.py` — 识别板2 文字识别（143 行）

识别板2 是「化验区 忙碌中 · 等待 8 秒」这类状态牌，需要读出**忙/闲**和**等待秒数**。

- ROI 固定 `(100,150,600,424)`、1280×720（`:17-19`）——板子在画面里的位置在赛前标定一次就固定
- 预处理：灰度 → 3×3 高斯去噪 → `adaptiveThreshold(GAUSSIAN_C, 11, 2)`，比全局阈值抗反光和半幅阴影（`:27-40`）
- Tesseract：`--oem 3 --psm 6 -l chi_sim`，PSM 6 按「单块文本」切分，两行排版不乱序（`:43-49`）
- 语义解析（`:52-71`）：关键词白名单 `空闲/通过` vs `忙碌/等待`；正则取 `(\d+)\s*秒`，只在 5–10 s 区间内采信，越界或缺省一律 8 s —— 板子给的就是 5–10 s，超范围说明 OCR 认错了数字
- 10 Hz 发布 `/board2_result=[is_busy, wait_s]` 与 `/board2_text`（`:76-77, 92`），带成功/失败计数，连续 30 次失败才告警一次（`:108-119`），避免刷屏

## 我在这份代码里解决的四个问题

1. **定位框数量硬阈值**：`== 48` → `40 ≤ n ≤ 56`。斜视、局部反光时少一两个框就整帧丢弃，是识别率的主要瓶颈。
2. **四象限与车窗朝向无关**：加 5° 旋转补偿 + 透视后镜像判断，解决「同一块板，车停不同侧解出的区域顺序相反」。
3. **识别时机的浪费**：识别从「到板前才开始扫」改为常驻扫描 + 服务返回缓存结果，任务节点到板即可决策，省掉等待帧的时间（4 min 限时下这段是纯收益）。
4. **识别失败不空跑**：3 s 无合法结果回退默认处方，比赛不因单次识别失败而中断流程。
