# 03 处方二维码识别

`F1_detect_code.py`（408 行）解决的是：一块贴有二维码的板子，车从任意姿态、任意距离看过去，都要稳定解出**四个区域的窗口组合**，并换算成「该去哪些窗口、几份样本、送哪个化验窗口」。

## 输入

```python
cap = cv2.VideoCapture("http://192.168.31.101:8080/stream?topic=/camera/rgb/image_raw")   # :101
```

直接用 `cv2.VideoCapture` 吃 `web_video_server` 的 MJPEG 流，而不是订阅 `/camera/rgb/image_raw` 话题。原因：

- 省一次 `cv_bridge`/`image_transport` 的编解码与消息序列化，单帧延迟更低
- 识别节点与相机节点完全解耦，识别挂了不影响导航，反之亦然
- 代价：IP 写死，换网络环境要改代码（`:102` 留了一行注释掉的本机 usb_cam 地址）

## 每帧处理链

### 1. 旋转补偿 5°（`:113-122`）

```python
angle = 5
matrix = cv2.getRotationMatrix2D(center, angle, 1.0)
frame = cv2.warpAffine(frame, matrix, (width, height))
```

车停在板前时车身不保证正对，固定 5° 逆时针补偿。5° 是赛前采集样张扫 0°/5°/10° 三档后取的最优值；写死是因为比赛只有一块板、一种停车姿态，没必要做自适应。

### 2. 定位框检测（`:137-195`）

四层筛选，从宽到严：

| 层 | 条件 | 行号 | 参数 |
| --- | --- | --- | --- |
| 0 | 轮廓面积在 `[min_area, max_area]` | `:143-148` | `min_area=500`, `max_area=20000`（`:35-36`） |
| 1 | `approxPolyDP` 后顶点数 == 4 | `:150-158` | `approxPolyDP_epslion=0.02`（`:33`），`peri` 按轮廓周长比例 |
| 2 | 正方形判定 `abs(w-h)/(w+h) < 0.4` | `:160-169` | `wh_rate=0.4`（`:34`），`minAreaRect` 的宽高比 |
| 3 | 两个正方形中心互相包含（`pointPolygonTest > 0`）且中心距 < 20 px | `:171-195` | `min_center_distance=20`（`:38`） |

第 3 层的产物 `dingweikuang` 是「一对嵌套正方形」，也就是二维码的**定位框（回字形）**：外框和内框的中心几乎重合，而板面上其他正方形图案不会有这种嵌套关系。这一层是整个检测的判别核心。

### 3. 定位框个数门限：`== 48` → `40–56`（`:196-202`）

```python
# 原条件: len(dingweikuang) == 48 (过于严格)
# 修改为: 定位框数量在合理范围内（大于40且小于56）
if (len(dingweikuang) >= 40 and len(dingweikuang) <= 56):
```

二维码有 3 个物理定位框 + 1 个校正图案，展开成嵌套对后理论上 48 个候选。实际：

- 斜视时背面的框投影变窄，`wh_rate` 直接筛掉
- 局部反光让内框边缘断裂，`approxPolyDP` 出 5 个顶点
- 板面贴纸有褶皱时包含关系判定失败

结果是「少一两个框」变成常态。`== 48` 是「必须完美」，`40–56` 是「大致正确」——用后续 4 区域解码成功率兜住误检风险，而不是在门限上死抠。

### 4. 透视归一化（`:239-248`）

从所有合格定位框的顶点里取四个极值点（min_x / max_x / min_y / max_y），投到 `600×600`：

```python
if min_x_index[0] < max_x_index[0]:
    goal_box_centers = [(50,550), (550,50), (50,50), (550,550)]
else:
    goal_box_centers = [(50,50), (550,550), (550,50), (50,550)]
M = cv2.getPerspectiveTransform(src_pts, dst_pts)
warped_img = cv2.warpPerspective(dingweikuang_frame, M, (600, 600))
```

那个 `if` 就是**镜像处理**：车从板的左侧看和右侧看，四个极值点的顺时针顺序是反的，不翻转的话四象限会和物理区域错位，解出的串整体镜像。

### 6. 投票与协议（`:305-391`）

```python
all_data = [img0_data, img1_data, img2_data, img3_data]      # :305
img_len = [0,0,0,0]
for k in range(4):
    if len(all_data[k]) < 4: img_len[k] = len(all_data[k])   # :309-317
max_img = max(img_len)          # 解出的字符数（0..3）
idx = img_len.index(max_img)    # 哪个区域（0..3，即板位）
```

设计要点：

- **字符数即样本数**：`A`/`AB`/`ABC` 分别代表 1/2/3 个窗口有样本，所以 `样本数 = 解的字符数`，不需要额外字段
- **板位即化验窗口**：解出字符数最多的那个区域序号 `idx`（0..3）就是样本类型 → 送哪个化验窗口（`lab_window = result[4]`）
- **非法串计数**：`Normal = ['A','B','C','AB','AC','BC','ABC','',[]]`（`:327-329`），不在集合里的串记 `Error_count = 该区域顺序号`（`:331-336`），作为质量指标上报
- 输出 6 字段：`[goC, goA, goB, 样本数, 板位, Error_count]`（`:340-391`）

注意 `img_len` 只在 `len < 4` 时记录，所以 `max_img` 的物理含义是「最长解码结果 = 3 个字符」，变量名 `img_len` 有误导；`max_img == 0` 时说明四块全空，**不发布**，任务侧靠 3 s 超时兜底（见 `01-任务链路与状态机.md` 步骤 8）。

## 服务化（`:78-99`）

```python
def return_result(req):
    global latest_msg
    if latest_msg is not None:
        pub_flag.publish(latest_msg)          # 重发缓存
        return TriggerResponse(success=True, message=str(latest_msg.data))
    return TriggerResponse(success=False, message="No result yet")
rospy.Service('/request_recognition', Trigger, return_result)
```

识别在车行进途中持续进行，到板前缓存里通常已有结果，服务只是「把最新结果再发一遍」。任务节点 `wait_for_service(3.0)` 后调用一次即可，省掉「到板才开始识别」的 1–2 帧等待（4 min 限时下这是净收益）。

另有 `:393-399` 每 0.5 s 重发一次缓存，覆盖「服务调用早于识别完成」的时序竞争。

## 时序与开销

- 单帧开销主要在 `findContours` ×2 + `pyzbar` ×4，1080p 下约几十毫秒量级（未做精确 benchmark，`待补`）
- 无 `rate.sleep()`，跑的是「读帧即处理、处理完再读」的自然节流——流是 25 fps 时处理速度低于它，等于自动丢弃多余帧，不会积压
- `cv2.waitKey(1)` + `imshow` 只在有 GUI 的调试环境可用，车上跑要保证 DISPLAY 可用或去掉这些调用（`:402`）
