# 05 一圈怎么跑：段序与跑圈效率

## 赛制是跑圈，不是跑一趟

一轮限时 **240 s**，小车按固定段序循环跑圈：

```
① 二维码识别区（读处方板）→ ② 采样区（体检窗口取样本）
        ↓
④ 化验区（提交样本）← ③ 化验区（读窗口空闲状态）
        ↓
⑤ 回起点 ── 开始下一圈
```

- 任务被拆成**一段一段推进**，每段都是「发导航目标 → 等结果 → 到点做动作」；代码里对应状态机 `count` 的 `9 → 10 → 11 → 9`（`:204`、`:232-239`），每跑完一圈回到 `9` 重新开始。
- **限时内完成的圈数才是成绩**，所以这一章关心的是单圈 95 s 花在哪、哪一段值得压，而不是「还剩多少时间」。

## 95 s 花在哪

| 环节 | 量 | 依据 |
| --- | --- | --- |
| 二维码识别段的固定等待 | **4 s** | `rospy.sleep(1.0)` + 3 s 轮询（`:277-289`），可从代码精确算出 |
| 每站停顿 | 0.25 s × 取样本窗口数 | `:216` |
| 回起点停顿 | 1.0 s | `:217` |
| 服务等待上限 | 3 s | `wait_for_service(3.0)`（`:261`） |
| 导航段 | 4–6 段，单段上限 30 s | `:448`；实际单段 10–15 s 量级（现场观察） |

结论：**95 s 里绝大部分是导航与车体动作**，识别与停顿是一个 10 s 量级的零头——真正决定圈速的是导航段数、每段耗时、以及识别一次成功的比例。

## 跑圈效率的四个杠杆（按收益排序）

1. **单段导航质量**（最大头）：地图与点位标定、`clear_costmaps` 的时机、30 s 卡死即放弃。一段慢 5 s，一圈就多 20–30 s。
2. **识别一次成功的比例**：二维码没解出来会走 3 s 回退默认处方（`:324-332`），代价不只是 3 s——默认处方可能让人白跑一两个窗口。95% 的成功率意味着每 20 圈大约有 1 圈要付这个代价。
3. **每圈固定的 4 s 识别窗**：这是唯一能精确回收的确定性开销。改成「收到合法结果即 `break`」可压到 1.5 s 左右，单圈省 2–3 s（约 3%）。
4. **圈数门槛**：240 ÷ 95 ≈ 2.5，即限时内能跑完 **2 个完整循环**；要摸到 3 圈需要单圈压到 **80 s 以内**（3 × 80 = 240）。这是量级变化的点——只有导航段整体提速才够得着，抠停顿和识别等待都到不了。

## 为什么简历里不写「余量」

跑圈赛制下，余量不是设计目标，是副产品。写「余量 60%」容易读成「跑得慢但没超时」；写**「单圈约 95 s，限时 240 s 内可完成 2 个完整循环」**才是赛制里的真实位置。

被追问「为什么不更快」时的正确答案：**瓶颈在导航段与车体动作，不在识别**。每圈固定的 4 s 等待和 0.25 s 停顿加起来不到 6 s，压到极限也只省 1 个量级的零头；要把 95 s 压到 80 s 以下，必须动导航参数或点位布局，那是风险更高的改动。

## 停顿压缩（`:215-217`）

```python
self.pause_time = 0.25       # 取样本/送药停顿（原 0.5 秒的一半）
self.home_pause_time = 1.0   # 回到起点（原 2 秒的一半）
```

注释明确写「原 0.5 秒的一半」「原 2 秒的一半」——这是针对圈速做的定向压缩，不是随手调的。但**量级要说清**：每圈省 1.5 s 左右，对 95 s 是 1.5%，改的是稳定性边界上的手感，不是成绩。

停顿时长本身不代表任务可省略：取样本/放样本的物理动作靠车体结构完成，停顿只是为了等动作稳定 + 让裁判端看到「停在该点」，0.25 s 是能稳定被抓拍到的最短值。

## 规则里的「化验区空闲识别」在实现里是什么位置

规则要求第三步先去化验区读窗口空闲状态、再决定提交到哪个窗口。实现上这一段是**独立的节点，没有接入任务决策**：

- `OCR_CAM.py` 以 10 Hz 发布 `/board2_result`（`[is_busy, wait_s]`）与 `/board2_text`（`:76-77`、`:92`），供操作手在终端/画面上判读；
- 任务节点 `F1_yaofang.py` **全文没有订阅 `/board2_result`**，送检窗口直接取处方板的板位字段 `result[4]`，经 `lab_positions = {0:6, 1:5, 2:4, 3:3}` 映射到化验区点位（`:399`）。

也就是说：车侧的送检路径是「按处方直送」，不是「先探空闲再选窗口」。这个差口是本届没做完的一项，根因与修法见 [`docs/04`](04-板2文字识别.md) 与 [`docs/06`](06-缺陷清单.md)。

## 卡死即放弃（`:446-453`）

```python
finished = self.move_base.wait_for_result(rospy.Duration(30))
if not finished:
    self.move_base.cancel_goal()
    return False
```

- 超时不重试、原地不等待，直接返回 `False`，调用方继续下一段
- 逻辑上「少一次取样本」比「卡在一段路上」强得多：这一圈少一段，下一圈还能重来
- 30 s 的取值依据：一圈 4–6 段导航，单段上限 30 s 时最坏 180 s 仍落在 240 s 内，不会因为一段卡住把整轮时间吃光

## `clear_costmaps` 的位置（`:254、:350、:354、:386、:390、:405、:409、:422`）

每次**发目标前**清一次，到达后**再清一次**：

- 发目标前清：车可能停在障碍物残留的膨胀层里，`move_base` 会直接判「起点在障碍物内」拒绝规划
- 到达后清：取样本/放样本时人或物体靠近过，留下的 costmap 会影响下一段规划

副作用是 AMCL 局部定位会跳一次——这就是上报用标定坐标的原因（[`02-裁判软件上报协议.md`](02-裁判软件上报协议.md)「位置上报的取舍」）。

## 识别的固定等待（`:277-289`）

```python
rospy.sleep(1.0)
max_wait = 3.0
while waited < max_wait and not rospy.is_shutdown():
    rospy.sleep(0.5); waited += 0.5
    ...（收集结果，但**不 break**）
```

到识别板后固定停 **1.0 + 3.0 = 4 s**，即使结果在第 1 个 0.5 s 就已经到了。没改的理由：结果在车微调位置期间可能更新，多等几帧能让「最新结果」更可信；当时判断 4 s 换稳定性是划算的。

若要优化，最小改法是收集到合法结果即 `break`、并把 `max_wait` 降到 1.5 s，预计单圈省 2–3 s。

## 口径提醒

- 95 s 是**现场观察**，没有逐圈日志，别写成「平均 93.2 s」这种看起来有日志支撑的精度。
- 简历/面试里说「单圈约 95 s，240 s 限时内可完成 2 圈」，**不要说「余量 60%」**——跑圈赛制里余量不是成绩。
- 「3 圈需要 ≤80 s」是算术推论，不是我们达到过的成绩，别混进成果里。
