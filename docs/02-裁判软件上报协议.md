# 02 裁判软件上报协议

`StateReporter`（`F1_yaofang.py:19-158`）是整车与裁判系统之间唯一的通道。裁判软件是 Windows 端的一个 TCP 服务，小车是客户端。

## 连接

| 项 | 值 | 行号 |
| --- | --- | --- |
| 裁判端地址 | `192.168.31.21:8888` | `:42-43`、`:171` |
| 连接超时 | `settimeout(3.0)` | `:71` |
| 重连间隔 | 5 s（`_report_loop` 内退避） | `:137`、`:141-145` |
| 上报频率 | 1 Hz（`start_reporting(1.0)`） | `:173` |
| 传输格式 | 单行 JSON，`\n` 结尾，`sendall` | `:117-120` |

连接失败**不阻塞主流程**：`connect()` 内部吞掉异常、返回 `False`，主线程照常跑任务，只由上报线程每 5 s 重试（`:61-79`）。这一点很重要——比赛现场裁判软件重启或网线松动的概率远高于小车死机，上报断了不能连带任务一起停。

## 报文

```json
{"id": "1", "speed": 0.0, "odom": [0.7, 2.55], "task": "A", "CV1": "WAIT-0", "CV2": "AB-2"}
```

| 字段 | 含义 | 取值 | 行号 |
| --- | --- | --- | --- |
| `id` | 车号 | `"1"`（本车） | `:108` |
| `speed` | 当前线速度 | `msg.twist.twist.linear.x`，保留 1 位 | `:53`、`:109` |
| `odom` | 上报位置 | `[x, y]`，保留 1 位小数 | `:110` |
| `task` | 当前阶段码 | `R`/`1`/`2`/`A`/`B`/`C`/`4`（化验窗口用 `1..4`） | `:26`、`:88-94` |
| `CV1` | 图像识别结果 1 | 本实现固定 `"WAIT-0"`，未接 | `:27` |
| `CV2` | 图像识别结果 2 | `"<窗口组合>-<样本类型>"`，如 `"AB-2"` | `:308-314` |

`task` 的语义是「我现在处于哪个任务点」，由每个阶段入口调用 `update_task()` 驱动（`:241-243`），同时往 `/current_task` 话题发一份相同内容（`:175`），方便其他节点/上位机观察。

`CV2` 的编码规则：三个窗口标志位 → `"C"`/`"A"`/`"B"` 拼接后按字母序排序（避免 `CAB`/`ABC` 两种顺序被判成不同结果），后缀是样本类型序号 0–3：

```python
windows_str = ""                       # :308-311
if self.windows_go[0]: windows_str += "C"
if self.windows_go[1]: windows_str += "A"
if self.windows_go[2]: windows_str += "B"
sorted_windows = ''.join(sorted(windows_str))     # :312
cv2_value = "%s-%d" % (sorted_windows, self.sample_type)   # :313
```

## 位置上报的取舍

`update_task_and_odom()`（`:88-94`）：

```python
if task_code in self.ideal_coords:      # 到达已知任务点
    self.odom = list(self.ideal_coords[task_code])   # 用标定坐标
else:
    self.odom = self.real_odom.copy()   # 行驶中/未知点位用实时 odom
```

`ideal_coords`（`:30-40`）就是 8 个任务点的官方坐标：`A(0.7,2.55)`、`B(1.5,3.05)`、`C(1.4,2.06)`、`1(-1.6,2.53)`、`2(-0.8,1.82)`、`3(-1.6,1.58)`、`4(-0.8,0.98)`、`R(0,0)`。

**为什么这样做**：每次 `clear_costmaps` 之后 AMCL 会重新做一次局部匹配，位置可能跳 3–10 cm；裁判端按坐标容差判「是否到位」，直接把跳动透传上去会让判定在边界反复横跳。到达任务点意味着车的真实意图位置就是标定点，上报标定值是把「抖动噪声」变成「确定值」。

**边界要说清**：只在 `update_task()` 被调用（即进入该阶段）期间生效，行驶中 `task` 仍是上一个点的编码——所以这不是「伪造位置」，而是「到点后以标定值为准」。面试被追问时按这个口径回答，别说成「我们上报的是理想坐标」。

## 线程模型

```
主线程：状态机 9→10→11→9，阻塞在 move_base action 等待
上报线程：daemon，while running: 每隔 interval 要么 send_data()，要么 reconnect()
```

- 上报线程是 `daemon=True`（`:131`），ROS Ctrl-C 时随主进程退出，不需要 join
- `reconnect_lock`（`:48`）只在 `connect()` 里用，防止重连与 `stop()` 并发关同一个 socket
- `send_data()` 里任何异常都把 `connected` 置 `False`（`:122-124`），下一轮循环自然转入重连分支——用「状态位」而不是「重试循环」表达失败，逻辑只有一处
- 注意 `:118` 的 `isinstance(json_str, unicode)` 是 Python 2 专有写法；迁 Python 3 要改成对 `bytes` 的处理（`json.dumps` 在 py3 返回 `str`，`sendall` 需要 `bytes`）
