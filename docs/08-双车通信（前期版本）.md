# 08 双车通信（前期版本）

本仓库的 3 个节点是单车闭环。**双车协同**是同一赛项前期的另一套实现，代码不在本仓库（基于厂商「信安源码」的 `Server_1017.py` / `Client_1017.py` 改造，见另一仓库）。这里只记录它与本仓库的关系，避免看 README 的人以为双车逻辑消失了。

## 当时的做法

两车通过 TCP 直连（`socket.AF_INET`，1 号车当 server、2 号车当 client），1 号车把识别结果打包成 6 个整数 `/cam_return` 发给 2 号车，2 号车据此决定去哪个窗口取样本——两车分摊窗口访问，把「一轮跑 3 个窗口」压成「各跑 1–2 个」，直接对抗 4 min 限时。

## 为什么本仓库没有它

比赛版收敛成**单车 + 裁判软件统一上报**：两车都直接向裁判软件（`192.168.31.21:8888`）报自己的状态（`id` 字段区分车号），协调责任交给裁判端，车际直连被去掉。理由：

- 车际直连多一层故障面（对方进程挂了、IP 变了），而裁判端本来就必须连
- 双车任务切分依赖现场发牌（哪辆车拿哪张处方），赛制上不一定可控
- 单车闭环已经能在 4 min 内跑完，双车的收益不足以抵消联调成本

## 双车版本里修的真问题（面试可讲）

`Server_1017.py:473-477` 是 `except socket.timeout: pass`，但全文从未调用 `settimeout()` ——**这个 except 永远不会触发**，`recv` 是永久阻塞的；超时分支还是 `pass`，不重置 `rec_data`，等于每秒重放同一条旧指令；对端正常关闭后 `recv` 立刻返回空串，`int('')` 抛异常或进入 100% CPU 忙等。

修法：`settimeout(1.0)` + 超时 `continue` + 判空告警退出线程 + `try/except ValueError` 包住 `int(rec_data)` + `SO_REUSEADDR`。

教训：**`except` 分支没有配套的触发条件，就是死代码**。这类问题 code review 时看不出来（语法对、逻辑「看着有」），只能靠「这条异常到底什么时候会被抛」逐条倒推。
